Start here

Agents fail late for reasons that happened early

An AI agent works in steps. It reads a message, calls a tool, reads the result, and decides what to do next. When a run fails at step 12, the error usually shows at step 12, but it was often caused earlier. Maybe a lookup at step 7 returned the wrong booking and everything after it built on that mistake.

Today you find that step by reading the trace and guessing, or by asking another AI to guess. The best published AI guessers get the exact step right well under half the time on the standard failure dataset.

Bisect tests instead of guessing. It rewinds the run to step 7, fixes that one thing, and plays the rest of the run again, several times. If the run now passes far more often than it does untouched, step 7 caused the failure. That is an experiment with a measured effect, not an opinion.

Record · rewind · fix · re-run state recording
Steps 1–6 are replayed from the recording at no cost. Step 7 gets one change. Steps 8–12 run live again. The failure at step 12 turns into a pass, so the blame goes to step 7, not step 12.
Part 1 · the engine

Record, snapshot, replay

Saves every model reply and tool result, plus a copy of the world state at every step. It can jump back to any step exactly, without spending a single model call on the steps before it.

Part 2 · attribution

The judge guesses, replay proves it

A cheap AI judge ranks the suspect steps. Bisect then tests only the top few with controlled re-runs and reports each step's effect with a 95% confidence interval.

Part 3 · the PR check

“This PR broke step 7”

A GitHub Action runs the agent's test scenarios before and after a change. If the pass rate drops, it posts a comment naming the step that broke and what changed there.

Why the name changed

“Rewind” is taken: agentoptics ships Rewind, the time-travel debugger for AI agents on PyPI as rewind-agent. Bisect names what the tool does: git bisect finds the commit that broke your code, and this finds the step that broke your run. One catch: bisect is already a Python standard-library module, so the package is agent-bisect, you import it as agent_bisect, and the command is bisect.

The claim this is all for

A number, a method, a repo

“On τ²-bench failures with a known planted cause, testing each suspect step by re-running it finds the right step X points more often than asking an AI judge, at a stated cost per diagnosis. Here is the dataset, here is the code, and make reproduce rebuilds every number offline from the recordings.”

Everything in this brief exists to make that sentence true, or to report honestly that it isn't.

The core idea

Replay the past exactly, sample the future

Cloud models are not repeatable: the same prompt at temperature 0 can still give different answers. So Bisect doesn't try to make the model deterministic. It splits the run in two:

Before step k: from the tape

Every model reply and tool result was recorded, so replaying steps 1…k−1 means reading them back. That makes zero network calls and gives an exact copy. The world state (τ²-bench's in-memory database) is restored from the snapshot saved at step k, and its hash is checked against the recording.

After step k: sampled live

The rest of the run is random by nature, so Bisect runs it N times and counts passes. It does this twice: once with the fix at step k (treated) and once untouched (control). Some failed runs pass on a plain re-run, and without a control you would blame a step for that luck.

effect(k) = P(pass | fix step k) − P(pass | step k as recorded)
P(pass | fix) treated pass rate over N re-runs P(pass | recorded) control pass rate over N re-runs blame = earliest step whose 95% CI lower bound > δ

“Earliest step that clears the bar” matches how the failure-attribution benchmarks define the decisive error: the first step where a fix would have saved the run. Fixing later steps can also help a little, because the agent gets a chance to recover. That is why Bisect takes the earliest step that clears the bar, not the biggest effect.

What it costs

Why the judge goes first

Testing every step costs roughly steps × re-runs × calls per re-run. On a free tier capped around 40 calls a minute, that adds up quickly. Let a cheap judge shortlist the suspects, then test only those.

The risk in the shortcut

If the judge leaves the real culprit off the shortlist, replay can never find it. So the report must show how often the true step was in the judge's top-m at all (recall@m), separately from the final accuracy. If recall is low, raise m. If raising m costs too much, that is a finding.

Stay honest about this

Where snapshots actually matter

In plain τ²-bench, tools are deterministic: the same database plus the same call gives the same result. There, you could rebuild the state at step k by re-running the recorded tool calls from the start, so snapshots mostly buy speed, not correctness.

Snapshots matter for correctness when tools aren't deterministic: generated IDs, timestamps, flaky services, anything with side effects. The build therefore includes a “flaky world” variant of τ²-bench (random IDs, time-dependent answers, occasional tool errors). There the no-snapshot baseline measurably drifts and Bisect doesn't. That ablation is what justifies the engine. Without it, “snapshots” is just a feature on a list.

The gap, stated exactly

Nobody combines world-state snapshots at every step, statistically sound counterfactual blame, a real benchmark with planted, known causes, and a PR verdict that names a step, for example “this PR moved the decisive step from 7 to 4; effect 0.62, 95% CI [0.38, 0.81].” CAR has the statistics without the rest; Mirrors has CI without blame; Rewind has forking without statistics.

Build our own, credit theirs

CAR is MIT-licensed and close to our core, but it is tiny, unpublished on PyPI, and re-runs tools live. Snapshots have to be designed into the engine from the start, so Bisect writes its own. It cites CAR as prior art and includes a CAR-style re-run-live mode as a baseline, so the comparison is on the page rather than implied.

Architecture

A core that knows nothing about blame

Two layers with a wall between them. The core records, snapshots and replays. Attribution sits on top. The core never imports attribution, so Branchpoint (project 04) can reuse it to fork runs.

Adapters feed the core. Attribution drives the core through one interface (restore, apply, run the rest). The surfaces only read results.

Where the right answers come from

Break runs on purpose

Public failure logs can't be re-run, and nobody labels why your own failures happened. So Bisect makes failures with a known cause: take a run that passed, break exactly one step, and keep it only if the break reliably causes the failure.

Record successes

Run τ²-bench airline + retail tasks, and keep the runs that pass (reward 1.0).

Check they're stable

Re-run the full task 4×. Keep tasks with a pass rate ≥ 0.75, so a failure isn't just noise.

Pick a step

Choose a tool-result step k at random (stratified early / middle / late).

Plant a fault

One of four: wrong value, missing field, stale record, or tool error text.

Re-run the rest

Sample the steps after k N=4 times with the fault in place.

Keep if it flips

Faulted pass rate ≤ 0.25. The label is k, and the fix is the original result.

Two kinds of fix

On planted faults the fix is known: put back the original tool result. That is an oracle, and it isolates the question “can replay find the step?”. On real failures nobody knows the fix, so repair.py asks a model to propose one, and the report scores both separately. Mixing them would hide which part failed.

The deciding constraint

Every model call is scarce

AcceptRate's constraint was memory bandwidth. Bisect's is model calls: a free tier around 40 a minute, shared by the agent, the simulated user and the judge. So one rule shapes the stack: every call goes through one rate limiter and one ledger, and is recorded. Nothing is ever paid for twice, and tests and the report never touch the network.

Five rules that outrank the table

Rule 01

Record everything, always

Every call, including judge and repair calls, is recorded before it's used. A crash mid-run loses nothing, and a resumed run spends nothing twice.

Rule 02

Tests never hit the network

pytest-socket blocks it. Unit tests use a scripted fake model with known causal structure; live calls live only in marked, opt-in smoke tests.

Rule 03

Divergence is an error

If a replayed request hash doesn't match the recording, stop and report it. Never quietly fall back to a live call. That is how replay tools silently lie.

Rule 04

Pin what moves

Model IDs, the tau2 commit and the user-simulator model are pinned in the run manifest. NIM can change or retire models; the recordings survive either way.

Rule 05

The key never leaves .env

NVIDIA_API_KEY lives in a git-ignored .env, is checked at startup, and is scrubbed from recordings and logs by a redaction test.

Design direction

  • Same Instrument tokens as AcceptRate (this page's palette), so the portfolio reads as one body of work.
  • Amber means blame, teal means measurement, green and red mean pass and fail, always paired with ✓ / ✕ glyphs.
  • An interval is always drawn next to its estimate; a point estimate never appears alone.

Deliberately smaller than AcceptRate

  • No Go TUI this time. The CLI prints plain summaries, and the viewer is the visual surface.
  • No live streaming: the viewer reads finished recordings, which keeps it simple and cacheable.

Deliberately not used

Docker

τ²-bench runs in-process; containers add nothing until a SWE-bench adapter exists.

OpenTelemetry as the source

GenAI conventions are still “Development”, and message content is off by default, so OTel traces usually can't be replayed. Export only.

A LangGraph dependency

An adapter later, maybe. The core stays framework-free so Branchpoint can reuse it.

Postgres · Redis · PyTorch

SQLite and files cover one machine. Nothing here trains a network.

Where the credibility lives

Rules that keep the number honest

Before measuring

  • Freeze the split first. Dev and test planted-fault sets are fixed, with a manifest hash, before any tuning.
  • Pre-register the settings: max N, δ, the shortlist size m and the stopping rule, written to docs/decisions/.
  • Always run a control. An effect without one is never reported.

When reporting

  • Accuracy comes with a bootstrap 95% CI, and so does the difference between methods.
  • Report recall@m, cost per diagnosis, and the cases where Bisect was wrong.
  • A failed gate stays failed, with its reason written up, as AcceptRate's P5 was.
